# claude-attribution

## Workflow: Anti-Slop First

Before composing ANY external post, follow this order:

1. **Compose** concrete, specific content — state what changed and why
2. **Self-check for AI slop** (see below) — remove any banned filler
3. **Structure review comments** as location -> problem -> proposed fix
4. **Append the attribution line** as the last line of the body
5. **Show the user** the complete post and get approval
6. **Post only after the user confirms**

## Banned AI-Slop Phrases (Blocked)

The hook blocks posts containing these phrases (case-insensitive). Never use
them in external posts:

- `this commit`, `in this PR`
- `comprehensive`, `robust`, `seamless`
- `great job`, `thanks for this`
- `I think maybe`, `you might consider`

Rewrite with plain, factual language. For example:

- ❌ "This is a comprehensive fix for the robust refactor."
- ✅ "The retry loop now backs off exponentially; added a regression test for the timeout path."

## Review-Comment Quality Pattern

Review comments MUST follow this structure:

> **location** -> **problem** -> **proposed fix**

Example:

> `app/services/billing.rb:42` -> the `unless` guard makes the early return
> unreachable -> invert the condition and return early.

## Core Rule

Every post to an external platform MUST end with:

> 🤖 Written by Claude, reviewed by \<name\>

Where `<name>` comes from `~/.claude/claude-attribution-name.txt`.

## Setup

On first use, if `~/.claude/claude-attribution-name.txt` does not exist:

1. Ask the user: "What name should appear in the attribution line?"
2. Save their answer: `echo "<name>" > ~/.claude/claude-attribution-name.txt`
3. Proceed with the original task

## What Counts as External Posts

ANY MCP tool call that includes a body/content/message field:

- GitHub: PR descriptions, issue comments, review comments
- JIRA: issue comments, issue descriptions
- Confluence: page content, comments
- Slack: messages
- Any other MCP-connected platform

Also CLI commands: `gh pr create`, `gh issue comment`, etc.

## How to Apply

1. Compose the post body (slop-free)
2. Append the attribution as the **last line** of the body:

   ```
   🤖 Written by Claude, reviewed by <name>
   ```

3. Do NOT add it to titles, labels, or metadata fields — only the body/content
4. For Bash CLI commands (`gh`, `curl`, etc.), always include the attribution **inline** in the body string — never use shell variable expansion like `${ATTR}` to inject it, because the hook inspects raw command text before shell expansion

## Commit Messages

The hook also blocks AI-generated trailers in `git commit` messages:
`Co-authored-by:` lines naming AI models, and `generated by/with <AI>` or
`assisted by <AI>` lines. Keep commit messages concise and factual.

## User Review Before Posting (Mandatory)

Before making ANY external post, you MUST:

1. Show the user the **complete post content** (including the attribution line)
2. Clearly state **where** it will be posted (platform, repo, issue number, channel, etc.)
3. Ask: "Ready to post this? (yes/no)"
4. **Only post after user confirms.** If user says no, ask what to change and revise.

This applies to ALL external posts — GitHub PRs, issue comments, JIRA comments,
Slack messages, Confluence pages, review comments, and any other platform.

Never skip this step. The attribution line says "reviewed by" — the user must
actually review it.

## When the Hook Blocks

If the PreToolUse hook blocks your post:

1. Read the error message — it names the exact problem (missing attribution, slop phrase, or AI trailer)
2. Fix the content accordingly (add attribution, rewrite slop, remove AI trailer)
3. Show the updated content to the user for review
4. Retry the tool call only after user approves
